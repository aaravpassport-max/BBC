# End-to-End Decision-Engine Audit — Cross-Factor Synchronization & Scalping Focus (2026-09-02)

## Scope and how this pass was scoped

The request was for a full end-to-end audit of every factor, rule, indicator, and failure condition, verified through realistic combined-condition fake trades, with special emphasis on scalping. Two honest scoping facts up front:

1. **This codebase already has an unusually large, prior-built audit-test suite** — 30+ dedicated "audit"/"verifier"/"inventory" test files (`fm-library-inventory-audit`, `phase8-adversarial-conflict-matrix-audit`, `interaction-sync-audit`, `report-accuracy-audit`, `system-wide-participation-sync-verifier`, `end-to-end-decision-engine-audit`, `extended-scenario-matrix-audit`, and others), together exercising thousands of real assertions against the real `evaluateBrain()`/`evaluatePreTradeFailureModes()` functions, not mocks. Re-deriving all of that from zero in this pass would duplicate work and burn budget without adding evidence. Instead, this pass started with a structured inventory of what that existing suite actually proves (see below), then built new, targeted tests specifically for the gaps that inventory surfaced — chiefly, **scalping-specific combined-condition behavior** and **cross-component consistency** (eligibility screen vs. the real pre-trade gate vs. the persisted report), which is exactly where the existing suite was thinnest.
2. **A full line-by-line audit of all ~193 factors individually was deliberately not repeated here.** That already exists (`docs/FACTOR_INVENTORY_AUDIT.md`, 188 live rows re-verified against a real run; `docs/FM_LIBRARY_INVENTORY_AUDIT.md`, 153-row FM catalogue, 116 wired) and is kept current by the existing suite. This pass is additive: it verifies *interaction*, *synchronization*, and *report accuracy*, per the request's own explicit instruction not to check components only individually.

All findings below are backed by either (a) real, cited existing test files and their real pass counts, or (b) a new test file built and run this pass: `tests/scalping-multi-condition-decision-audit.test.js` (19/19 passing, run with `node tests/scalping-multi-condition-decision-audit.test.js`). Every number quoted was actually observed running the real code in this session — none is estimated.

## 2. New findings this pass (real evidence, `tests/scalping-multi-condition-decision-audit.test.js`)

### 2.1 The trade-type weighting mechanism is real and correctly wired into the actual decision — confirmed by direct execution, not just code reading

`evaluateBrain()` computes a raw `directionalScore`, then (since a prior session's fix) applies `computeTradeTypeDirectionalWeightedScore()` under the category weights in `FNO_TRADE_TYPE_CATEGORY_WEIGHTS` (scalping: Microstructure 1.6x, Flow 1.4x, Vol 1.3x, Tech 1.3x, Fundamental 0.5x, Regulatory 0.7x, Decay 0.6x, Greeks Deep 0.8x) and, via `applyTradeTypeWeightingAdjustmentToDecision()`, **can genuinely downgrade an already-decided `BUY_READY`/`SELL_READY` to `WAIT` (or relabel High confidence to Medium)** when the trade-type-weighted score no longer clears the threshold the raw score crossed. This is wired at `fno-lab-core.js:11408-11409` and does affect the real `decision`/`confidence`/`reason` returned to every caller — confirmed by tracing the exact assignment, and by directly exercising the real function (Scenario 1b): a raw score of 11.5 (crosses `BUY_THRESHOLD=11`) with a scalping-weighted score of 9.0 correctly downgrades to `WAIT`, with `reason` explicitly stating "Downgraded... under scalping's own real, documented category weighting."

**A caveat found while building this test, reported honestly**: engineering a *fully organic* ctx (not a direct function call) that lands inside the narrow window where raw crosses but scalping-weighted doesn't proved harder than expected within this pass's time budget — most of this engine's ~193 factors are coarse, discrete pass/fail contributors (0.3–1.5 points each), so nudging one category's ctx inputs tends to jump the raw score by 4+ points in one step rather than landing in a 1-2 point window. Scenario 1a (organic ctx) landed at raw=10.5→14.5 with no finer lever found; Scenario 1b (direct function call, still the real production function) proves the mechanism itself. **This is not evidence the mechanism is broken** — Scenario 2, run organically, independently confirms the weighting computation is real and responsive (Tech/Vol-dominated BUY_READY correctly stayed BUY_READY, unweighted score 16.40, unchanged under scalping). It is a gap in *this pass's* organic-scenario coverage, worth closing in a follow-up with more precisely engineered ctx composition (or a small helper that scales an already-computed real `results` array to hit an exact target score, rather than tuning raw inputs blind).

### 2.2 CONFIRMED, REPRODUCIBLE FINDING — the eligibility screen and the real pre-trade gate can disagree on the exact same trade, same refresh, and the report has no way to show this

This is the most consequential finding from this pass, and it is real, not hypothetical — reproduced directly (`tests/scalping-multi-condition-decision-audit.test.js`, Scenario 3):

- `evaluateBrain()` — the function whose `.decision` drives the visible "🟢 BUY READY" eligibility screen the user watches — **never calls or considers `evaluatePreTradeFailureModes()`** (the ~150-entry Failure-Mode Library, FM001–FM153) at all. Traced directly: the only Failure-Mode-*sounding* mechanism inside `evaluateBrain()` is `applyFailureLibraryAdjustment()`, a **different, similarly-named mechanism** based on historical regime win-rate statistics (`ctx.failureStatsByRegime`) — not the individual per-trade FM check catalogue.
- The real per-trade FM catalogue (`evaluatePreTradeFailureModes()` + `adjustFailureModesForTradeType()`) is called from exactly one place in the whole codebase: `tryOpenAutoTradePosition()`, at the moment a trade is actually about to open (`fno-lab-core.js:13815-13816`), and it genuinely gates the open (`finalAction==='block'/'reject'` prevents the position from opening).
- **Built a real, concrete scalping trade** where both are true simultaneously: `evaluateBrain()` returns `decision:'BUY_READY'` (comfortable directional score, no critical fails) for a leg that also has two independent, real order-rejection risk signals (spread 22% of bid, order qty 50 > resting ask qty 10). Calling the exact real function `tryOpenAutoTradePosition()` calls (`evaluatePreTradeFailureModes` + `adjustFailureModesForTradeType('scalping')`) on this same leg/ctx returns `finalAction:'block'` via FM025 (critical, "order rejection risk model").
- **Consequence**: on the same refresh, for the same trade, the eligibility screen shows "🟢 BUY READY," while an actual attempt to open it is silently blocked with a completely different, liquidity-based reason shown only in a separate, transient UI panel (`failureModeLibraryBox`) and a `reportFn()` log line — never reflected in the main decision badge, and (see 2.3) **never persisted anywhere** if the block happens, so there is no report to later reconcile against.
- This is very likely intentional architecture, not an oversight — the code comments around the real call site explicitly describe FM library verdicts as gating trade-*opening*, separate from the eligibility/scoring display. But it is **not documented as a known, expected UI/report inconsistency anywhere found in `docs/PENDING_REQUIREMENTS.md`**, and it directly matches the exact failure class the audit request called out: *"The eligibility/decision screen shows one result while the report shows another."*
- **Recommendation**: either (a) surface a lightweight "pre-trade gate: X condition(s) may block opening" indicator alongside the main eligibility screen whenever any FM-catalogue condition is currently active for the selected strike (computed on every refresh, not only at open-attempt time), or (b) explicitly document this as intentional in the UI copy/help text, so a user watching "BUY READY" isn't surprised when an open attempt is silently rejected for an unrelated reason.

### 2.3 Confirmed gap: a blocked trade attempt leaves no persistent report

Traced directly: when `tryOpenAutoTradePosition()` is blocked by the FM gate, it returns `{opened:false, failureModeResult: fmResult}` and nothing is written to any persisted store (journal, trade history). The only record is a transient `reportFn()` log message and a UI panel overwritten on the next refresh. By contrast, when a trade **does** open, `failureModeCheck` (the real FM result) and `tradeTypeWeighting` are correctly persisted onto the saved trade's `entrySnapshot` (confirmed directly, Scenario 8 — `buildEntrySnapshot()` produces a real snapshot, and the real call site's later `Object.assign(...,{failureModeCheck})` genuinely adds new information rather than silently colliding with an existing field of the same name).

This means the audit request's own explicit ask — *"the report should show... conditions that should result in rejection"* — cannot currently be satisfied for a rejected trade, only for an opened one. There is no rejected-trade report to audit for accuracy, because none is generated. This is a real, traceable gap, not a report-accuracy defect in an existing report.

### 2.4 Confirmed correct: simultaneous FM conditions do not suppress or dedupe each other under scalping escalation

Built a real leg producing two independent, simultaneous FM triggers — FM023 (wide spread, scalping-relevant) and FM025 (order rejection, independently critical) — and ran both through `adjustFailureModesForTradeType(..., 'scalping')`. Confirmed: both conditions survive distinctly in the triggered list (FM023 correctly escalated from `high/reduce_position_size` to `critical/block` with a `typeRelevance:'scalping'` tag; FM025 remains independently critical), and `finalAction` correctly resolves to `block` — the more severe condition is never masked by the escalation logic applied to the other.

### 2.5 Confirmed correct: no stale-state leakage across consecutive scalping refreshes

Ran the same underlying scalping ctx through two consecutive evaluations — refresh 1 with a wide, rejection-triggering spread (blocks), refresh 2 with the spread genuinely normalized (should clear). Confirmed the block lifts cleanly on refresh 2 with no leftover FM025/FM023 from refresh 1 — each evaluation is freshly, independently derived from the current leg, never cached or sticky. This matters specifically for scalping given its real 15-second poll cadence (`AUTONOMOUS_POLL_MS_BY_STYLE.scalping = 15000`).

### 2.6 Confirmed by design, not a bug: RSI-overbought-during-a-confirmed-uptrend does not fire FM014 on a BUY

While tuning a "conflicting indicators" scenario (RSI overbought + a BUY), found that the real RSI factor deliberately treats "overbought AND EMA9>EMA21 confirms a genuine uptrend" as `pass:true` ("strong momentum, not an automatic reversal signal"), which structurally prevents FM014 (which requires `rsi.pass===false`) from ever firing in a genuinely confirmed uptrend. This is the same mutual-exclusivity `end-to-end-decision-engine-audit.test.js`'s own Scenario 6 already confirms from a different angle. Not a defect — flagged here because it was initially mistaken for a possible gap during scenario construction, and is worth stating explicitly so it isn't rediscovered as a "missing warning" in a future pass.

### 2.7 Observation (not a bug): the "Microstructure" category label mixes two genuinely different data sources

The 10 rows tagged `cat:'Microstructure'` are not uniformly daemon-fed. Eight rows (Iceberg, Cumulative Delta, POC, Order Flow Imbalance, Footprint, Tick Speed, DOM Spoofing, VWAP Bands) are correctly, honestly `pass:null`/`score:0` whenever the companion tick daemon has no recent snapshot — confirmed directly. Two rows — **Futures vs Spot Premium/Discount** and **Market Depth Top 5 Bids/Ask** — are independently sourced from `ctx.futuresPrice`/`ctx.marketDepth` and can score real, non-zero directional points **completely independent of whether the daemon is running**. Since scalping applies a single 1.6x weight to the whole category, a user who sees "Microstructure daemon offline" might reasonably assume the whole category is contributing nothing to their scalping decision — which is not accurate for these two rows. Worth a small documentation/UI clarification (e.g., separating "Daemon-fed" vs. "Structural" sub-labels within the category display) but not a scoring defect — every row's own honesty (real data → real score; missing data → `pass:null`) is individually correct.

## 3. Direct answers to the audit's own "system completeness" checklist, based on evidence gathered

- **Which factors are working correctly?** All spot-checked factors (RSI, Microstructure's 10 rows, Fundamental/Decay/Greeks-Deep categories used to build the weighting scenarios) computed honestly and consistently with their own documented rules; no fabricated pass/fail observed in any new scenario this pass.
- **Which failure conditions are working?** FM023, FM025, FM014 all confirmed firing/not-firing exactly per their documented conditions, including under simultaneous/combined circumstances (2.4) and across refreshes (2.5).
- **Which rules conflict with each other?** None found conflicting incorrectly. The one apparent "conflict" (2.6, RSI overbought during BUY) is resolved correctly by the RSI factor's own trend-confirmation logic, not a bug.
- **Which components are duplicated / confusingly named?** The "Failure Library" (regime win-rate feedback, inside `evaluateBrain()`) and the "Failure-Mode Library" (the ~150-entry FM catalogue, `evaluatePreTradeFailureModes()`) are two real, different mechanisms with confusingly similar names — this naming collision is very likely why the eligibility-screen/pre-trade-gate disagreement in 2.2 has not been caught before: it's easy to read "Failure Library was reconnected into the decision" (true, for the regime-stats mechanism) and reasonably but incorrectly assume the FM catalogue was reconnected too (it was not, and by design is not).
- **Which report sections are missing information?** Rejected/blocked trade attempts have no persisted report at all (2.3) — the single clearest gap against the audit's own report-completeness requirements.
- **Which decisions cannot be properly explained by the report?** A `BUY_READY` eligibility-screen decision cannot be reconciled against a same-refresh FM-catalogue block, because the eligibility screen's `reason` field never mentions FM-catalogue conditions at all (2.2) — this is explainable from source, but not from the report/UI a user actually sees.
- **What needs to change to make the system fully coherent?** Primarily 2.2 and 2.3: either compute and surface the FM-catalogue verdict alongside the eligibility screen on every refresh (not just at open-attempt time), or explicitly document the two-gate architecture; and persist blocked-attempt records so a "why was I blocked" report exists after the fact, matching the persistence already given to opened trades.

## 6. UPDATE (2026-09-02, follow-up pass): §2.2 and §2.3 fixed

Per direct user instruction to fix the findings above, both concrete gaps identified in this report were closed with real code changes to `assets/fno-lab-core.js` (plus one HTML panel addition in `assets/standalone-app.php`). §2.4–§2.7 required no code change (already confirmed correct/by-design above).

**§2.2 fix — `evaluateBrain()` now computes and returns `brain.pretradeGateCheck` on every refresh.** New function `computePretradeGateCheck(decision, pseudoBrain, ctx, tradingType)` reuses the exact same real `simulateOrderRejection()` / `evaluatePreTradeFailureModes()` / `adjustFailureModesForTradeType()` functions the real trade-open call site (`tryOpenAutoTradePosition()`) uses, for the identical leg the eligibility screen just decided on. It is **purely additive/informational** — it never mutates `decision`/`confidence`/`reason`. This was a deliberate design change from the first implementation attempt: an earlier, mutating version (downgrading `decision` whenever any FM-catalogue `block` condition fired) was caught by this session's own full regression suite double-penalizing benign, already-otherwise-reflected partial-data conditions (e.g. FM013's "fewer than 21 candles" firing on ordinary partial refreshes this app's own coverage-based confidence downgrade already accounts for separately) — see `computePretradeGateCheck`'s own in-code TRACE comment for the full self-caught story. A second issue was caught the same way: the first working version of `pseudoBrainForGateCheck` omitted `factorRegistry`, causing FM072 (and structurally, FM057/FM081/FM082) to silently never fire in the gate check despite firing in the real open-time gate — found via this fix's own audit test (`Scenario 3`'s triggered-list identity assertion), fixed by adding `factorRegistry: registry` to the pseudo-brain object.

**§2.3 fix — blocked/rejected trade attempts are now persisted and displayed.** New `STORAGE.blockedAttempts` localStorage key (`fno_blocked_attempts_v1`), new `logBlockedTradeAttempt()`/`loadBlockedTradeAttempts()` helpers (reusing the existing `load()`/`save()` array-persistence pattern already used for `STORAGE.journal`/`STORAGE.daily` — no new storage mechanism invented), capped at 200 most-recent entries. Wired into the real block site inside `tryOpenAutoTradePosition()` (`if (fmResult.finalAction === 'block' || fmResult.finalAction === 'reject')`) — each entry records strike, option type, trading type, last price, `finalAction`, and the real triggered FM condition list (id/severity/action/reason). New `renderBlockedAttemptsHistory()` renders this log (most-recent-first, capped at 20 rendered rows) into a new `#blockedAttemptsHistoryBox` panel added directly under the existing Failure-Mode Library card in `assets/standalone-app.php`, called both at block time (same-refresh visibility) and on page load (so history survives across reloads, not just the last attempt).
