## 1. Trade Types Supported

The codebase's `fnoSettings.get().tradingTypes` object and `getEffectiveTradingType()` (`fno-lab-core.js:81`) genuinely distinguish exactly three trade types today:

| Trade type | How it's identified in code | Position path |
|---|---|---|
| **Intraday** | Default effective type when neither Scalping nor Swing toggle is on | Local, single-slot (`STORAGE.autoTrades`), same-day square-off required |
| **Scalping** | `fnoSettings.get().tradingTypes.scalping === true` | Same local single-slot as Intraday — Scalping and Intraday currently **share one position slot** (per the handoff, this is a known, documented limitation, not a bug) |
| **Swing** | Explicit `isSwingPath` flag, independent of the Scalping/Intraday toggle | Server-side, `wp_fno_open_positions` table, multi-position-capable, monitored independently (including by the standalone driver's `checkAndMonitorSwingPositions()`) |

**Positional and Short-term, as separate first-class types, do not exist in code today.** Per the Master Roadmap's Part A.1 decision, these are treated as natural extensions of Swing's existing server-side, multi-day position infrastructure rather than rebuilt from scratch — a genuine "Positional" mode is architecturally very close to "Swing with a longer minimum hold and different re-entry cadence," and will be added as a real, distinct `tradingType` value once the core three are fully correct (this is Phase 4+ work, not yet done). **Delivery, for F&O options specifically, is not a meaningful distinct category** — there is no equity-style share delivery for options; a position is either closed before expiry or exercised/settled at expiry, which today's Swing/expiry handling already covers. This document treats "Positional" as the placeholder name for that future fourth type and does not invent rules for it that aren't yet backed by code.

## 2. Market Regime Taxonomy

`computeMarketRegime()` (`fno-lab-core.js:4399`) builds a regime label from two independently-computed dimensions, plus overlays:

- **Trend**: Bullish / Bearish / Sideways, from the EMA9-vs-EMA21 percentage difference on the primary chart's closes (>0.1% = Bullish, <-0.1% = Bearish, else Sideways).
- **Volatility**: Low Vol / Normal Vol / High Vol, from India VIX when available (< 13 / 13-20 / > 20), falling back to 20-period realized (historical) volatility when VIX is unavailable (< 12% / 12-22% / > 22% annualized).
- **Expiry overlay**: label gets a `(Expiry)` suffix when `ctx.isExpiry` is true.
- This gives a base label like `Bullish-High Vol` or `Sideways-Normal Vol (Expiry)` — **9 base combinations × 2 (expiry/non-expiry) = 18 base labels**, not literally "16 states," but close to the handoff's stated figure; the discrepancy is not investigated further here since it doesn't affect correctness, only documentation precision.
- **`specialCondition`** (additive, doesn't change `label`): currently detects `'Panic'` — High Vol **and** broadly negative market breadth simultaneously (the codebase's own reasoning: a single stock driving high VIX isn't the same as a market-wide panic, and this needed real breadth data to distinguish, which is why it was built after the base 3-dimension model).
- **`extendedStates`** (additive): breakout/breakdown condition, distance from max pain, sudden-volatility-event flag, and a reversal-signal flag, layered on top of the base trend/vol/expiry classification.

**How trade types should use regime differently (design guidance for Phase 4, not yet all wired):** Scalping cares about the *current instant's* regime almost exclusively (a regime shift mid-scalp is a reason to exit, not just note). Intraday cares about the regime at entry and whether it holds through the square-off window. Swing needs regime *stability* over the intended hold — a regime that's expected to flip (e.g. approaching a known event) is a bigger risk factor for Swing than for Scalping, inverted from how most single-session risk factors behave.

## 3. Indicator & Factor Catalogue

The engine defines roughly 247 individual scoring statements across `evaluateBrain()` and 15 delegate `compute*Factors()` functions (confirmed by direct count in the Phase 1 audit; the `factors.json` catalogue lists 193 as a curated static reference, not a 1:1 map to the live code). Rather than document all ~247 individually here (that duplicates the codebase itself with no added value), this section documents each **indicator family** — the actual signal-generating logic — with the properties your Phase 2 spec asked for. Full per-statement detail (exact factor names, file:line) is in `docs/AUDIT_FINDINGS.md` §1/§5 and remains the canonical low-level reference.

### 3.1 Trend / Direction Indicators

| Indicator | Computation | Lag | Best conditions | Poor conditions | Recommended by trade type |
|---|---|---|---|---|---|
| EMA9-vs-EMA21 crossover / price-vs-EMA21 / price-vs-EMA50-daily | Recursive exponential smoothing of closes, 3 separate scored checks on the same underlying trend | Lagging | Trending markets (the thing it's measuring) | Sideways/choppy markets — will whipsaw and generate contradictory 1-candle flips | All three, but weight down for Scalping (too slow for a scalp's holding period) and rely on it more for Swing |
| HH/HL structure (20-candle swing proxy) | Direction of higher-high/higher-low pattern over a 20-candle window of closes (explicitly documented in-code as a close-based proxy, not a true high/low structure) | Lagging | Established trends with clean structure | Choppy ranges, gap-heavy sessions where close-only misses real intrabar structure | Swing primarily; weak signal for Scalping given the 20-candle lookback |
| Fibonacci retracement level | Proximity of spot to a retracement ratio of the same 20-candle range HH/HL uses | Coincident | Pullback-continuation setups within an established trend | No trend context (a Fib level in a sideways market is close to meaningless) | Swing; should always be read together with the trend check, never standalone |

**Redundancy note (Phase 1 audit §2):** these three, plus HH/HL and Fibonacci sharing one 20-candle input, are not deduplicated in code today. Not a bug — genuinely distinct math — but their agreement should not be read as 3-5 independent confirmations; see §6 (Redundancy/Correlation).

### 3.2 Momentum / Oscillator Indicators

| Indicator | Computation | Lag | Best conditions | Poor conditions | Recommended by trade type |
|---|---|---|---|---|---|
| RSI(14, Wilder) level + divergence | Bounded ratio of avg gain/loss, Wilder-smoothed; divergence checked over a 20-candle lookback | Lagging (despite "overbought/oversold" framing — the smoothing itself is backward-looking) | Range-bound markets for the level check; any market for genuine divergence | Strong trends (RSI can stay "overbought" for extended periods in a strong uptrend — the classic RSI trap) | All three; Scalping should weight divergence over level (level check is too slow) |
| MACD(12,26,9) crossover | Doubly-lagging — EMA-of-EMA-difference, then a third EMA on the histogram | Lagging | Established, sustained trends | Choppy/sideways markets (frequent false crossovers) | Swing/Intraday over Scalping — its own multi-EMA smoothing makes it too slow for a genuine scalp |

### 3.3 Volatility Indicators

| Indicator | Computation | Lag | Best conditions | Poor conditions | Recommended by trade type |
|---|---|---|---|---|---|
| Bollinger Bands (squeeze + position, 20,2) | Rolling mean ± multiplier·stdev of closes | Lagging (rolling-window based) | Squeeze → expansion setups (coincident volatility read, not a leading signal despite common trader framing) | Fast-moving, already-trending markets where bands are already wide | All three; squeeze specifically useful as a pre-Scalping/Intraday setup trigger, not a standalone entry signal |
| Historical (realized) volatility, 20-period annualized | Stdev of trailing log returns × √252 | Lagging | Regime classification (feeds `computeMarketRegime`'s volatility dimension as a VIX fallback) | Should never be used as a standalone entry trigger — it's a regime/context input, not a signal |
| Implied Volatility (from live option premium via BSM) | Solved from the live option premium, not from price history | **Leading** — the strongest forward-looking signal family in the engine | IV percentile extremes (mean-reversion setups), regime/risk gating | Deep ITM/OTM strikes where the solver can struggle to converge (documented technical gap) | All three; especially valuable for Swing (theta/vega exposure compounds over a multi-day hold) and for gating entries generally (IV percentile extremes feed FM014/FM014b) |

### 3.4 Flow / Positioning Indicators

| Indicator | Computation | Lag | Best conditions | Poor conditions | Recommended by trade type |
|---|---|---|---|---|---|
| OI Change % (CE/PE) | Net change in open interest this session | Coincident | Confirming a move already underway, feeding Operator Intel's trap/buildup signal | Standalone directional signal — it confirms, it doesn't predict | Intraday/Scalping (session-fresh flow); less relevant for Swing (which cares about multi-day OI trend, not one session's delta) |
| PCR (level + 30-min change) | PE OI / CE OI, and its rate of change | Coincident/contrarian-lagging | Extreme readings as contrarian context | Trending markets where PCR can stay skewed for a long time without reverting | All three as context, none as a standalone trigger |
| Max Pain / distance from max pain | OI-weighted strike where option writers' aggregate payoff is maximized | Coincident (static snapshot statistic, not a forecast) | Expiry-week pin-risk context | Far from expiry (max pain's pull is weakest early in a series) | All three, weighted up near expiry regardless of trade type |
| Best bid/ask qty imbalance | Single order-book level snapshot | **Leading** (near-real-time) | Immediate execution-quality/timing decisions | Broad market direction (it's a single-level microstructure read, not a market-wide signal) | Scalping most of all; genuinely useful for Intraday entries/exits, marginal for Swing |
| Microstructure daemon metrics (cumulative delta, POC, order-flow imbalance, iceberg/spoof detection) | Tick-level, from the optional companion daemon | **Leading when live** | Scalping entries/exits specifically | Currently: **always** — hardcoded `score:0` regardless of daemon status, so this genuinely leading data contributes nothing to the decision today (Phase 1 audit finding; not yet fixed — see §8 backlog) | Scalping by design, once actually wired in |

## 5. Position-Management & Paper-Trading Components

- **Entry**: gated by market-hours check → time-sufficiency check (`checkSufficientTimeRemaining`) → Failure-Mode Library (`evaluatePreTradeFailureModes` + `adjustFailureModesForTradeType`) → target/SL sanity check, in that order, for both the browser Auto-Trade path and (as of Phase 1) the standalone driver.
- **Exit**: `checkTradeExit()` — target/SL crossing — shared identically by browser and driver paths (this one was never trade-type-gated to begin with, correctly, since target/SL crossing is trade-type-agnostic by construction).
- **Square-off**: browser path checks `brokerSquareOffTime` (user-configured, defaults conservatively to 15:15) against live time; driver path currently relies on `checkSufficientTimeRemaining`'s entry-side gate but does not yet have its own explicit forced-square-off exit trigger for an already-open position that runs past the deadline (**gap — Phase 5 backlog, see §8**).
- **Paper trade simulation**: real Zerodha-rate-accurate brokerage/STT/stamp-duty/GST modeling, real bid/ask-cross fill-price modes (theoretical vs realistic), real order-rejection-risk simulation (`simulateOrderRejection`) and real volatility-scaled execution-latency cost (`simulateExecutionLatency`) — this is a genuine strength already confirmed working in Phase 1's regression (all these tests pass in the existing 674-large suite).
- **Learning/feedback (existing, before Phase 6's expansion)**: `computeRegimeWinRate`/`applyRegimeAdjustmentToDecision` and `computeTradeTypeWinRate`/`applyTradeTypeAdjustmentToDecision` — both real, already-tested, sample-size-gated (won't downgrade on a tiny sample), and both correctly wired into the live decision (confirmed in the Phase 1 audit's connectivity check). This is the existing foundation Phase 6's larger, more structured learning loop will build on, not replace.
