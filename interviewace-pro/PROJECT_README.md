# InterviewAce Pro — v3.0.0

Enterprise-hardening pass on the original InterviewAce WordPress plugin, built from the gap analysis of the uploaded zip. Two parts:

- `php-plugin/` — the original WordPress plugin backend, with the audit fixes applied directly (see inline `ROOT-CAUSE FIX` / `SECURITY FIX` comments throughout for exactly what changed and why).
- `frontend/` — a brand-new Vite + React + TypeScript source tree replacing the old minified-only `react-app/dist/app.js` (the original zip had no `.jsx`/`.tsx` source at all).

## IMPORTANT — build verification status

This sandbox's `npm install` is blocked by an organization network policy (403 from the npm registry), so **I was not able to run `npm install`, `tsc`, or `vite build` myself**. The frontend code was written carefully and reviewed by hand for type correctness, but that is not the same as a mechanically verified build. **Before you trust this in production, run the build yourself** (see below) and fix whatever TypeScript surfaces — treat this as a strong first draft that needs a real compile pass, not a shipped artifact.

## Building

```bash
cd frontend
npm install
npm run build      # runs tsc --noEmit, then vite build
```

`vite build` outputs directly into `../php-plugin/react-app/dist/app.js` and `app.css` (see `frontend/vite.config.ts`), matching exactly what `interviewace.php` already enqueues — no PHP changes needed to pick up a new frontend build.

For local development against a real WordPress install:

```bash
cd frontend
VITE_API_BASE=https://your-site.test/wp-json/ia/v1 npm run dev
```

## What's implemented vs. what's next

**Backend (php-plugin/) — done across both passes:**
- Claude model ID made admin-configurable (was hardcoded, a production-outage risk) + retry/backoff
- Turn idempotency (unique DB key + safe-replay logic) — fixes duplicate-submit/retry corruption
- Report retry endpoint — fixes the "failed report is a permanent dead end" gap; its response now always includes `report_id` (a gap found this pass while wiring the "view from history" flow — the retry button needs an id it wasn't being given)
- Cron schedule bugs fixed (`monthly`/`weekly` weren't registered WP-Cron intervals; daily cleanup was never scheduled) + self-healing check
- Deepgram/ElevenLabs keys moved server-side (`api/class-api-speech.php`) — were previously shipped to every visitor's browser
- CORS locked from wildcard to an allow-list
- Google OAuth token-in-URL fixed (one-time code exchange instead)
- OTP brute-force throttling added (previously unthrottled)
- `pdftotext` now runs under a timeout + memory cap
- `/health` no longer leaks integration config to anonymous callers
- DB migration path: version-checked on every load, not just activation, with a dedup step for the new unique key so it's safe on an existing production DB
- **New this pass — found by cross-referencing every query against the real schema, not just the original audit's list:** `IA_API_Interviews::do_end()` was inserting usage minutes into a column called `date` that doesn't exist on `ia_usage` (it's `month_year`-keyed) — every interview completion silently failed to record usage, so monthly minute quotas for paid plans were never actually enforced. `IA_API_Profile::stats()` and `IA_API_Billing::status()` had the identical bug reading it back, plus a semantic mismatch (reporting a "daily" limit when the real free-plan rule is weekly). All three now go through one correct, shared implementation. Separately, the Razorpay webhook handlers were inserting `event_type`/`razorpay_event_id` into `ia_payments`, columns that didn't exist — every webhook-driven payment record was silently dropped, so `/billing/invoices` was permanently empty for any real paying user. Added both columns plus a uniqueness constraint on the event id (Razorpay retries webhook delivery, so this needed to be genuinely idempotent, not just column-present — caught and fixed a follow-on bug in my own first attempt at this, where the dedup key I chose would have collided across different months' real charges for the same subscription).

**Frontend (frontend/) — done across both passes:**
- Auth: register → OTP verify → login → forgot-password → Google OAuth callback (using the new safe code-exchange flow)
- Onboarding (target role → resume upload → JD paste, every step skippable — the backend never required any of this to create an interview, so the UI doesn't force it either)
- Dashboard with real stats (avg/best score, streak, weekly quota) instead of placeholder text; links to History/Settings/Billing
- Interview setup → live interview (idempotent turn submission wired to the backend's retry-safety fix, explicit "Priya is thinking" state instead of a silent hang, optional voice recording via the new speech proxy, typed-answer fallback that needs no mic permission)
- Report screen, including the "Regenerate report" action wired to the retry endpoint for a `failed` status; reachable both directly (`/report/:id`) and from history (`/history/:interviewId` resolves the report id first)
- History (paginated), Settings (profile edit), Billing (plan cards, Razorpay checkout, invoices, cancel)
- Design token system (`src/styles/tokens.css`) — the old CSS had zero custom properties; every color/spacing/radius here is token-driven
- In-memory access token + transparent silent-refresh-and-retry-once on 401 (client-side half of not getting logged out mid-interview)

**Third pass — done:**
- **Gamification was completely dead code.** `IA_API_Gamification::after_interview_complete()` (the entire XP/badge-awarding function) was fully written but never called from anywhere in the codebase — the screen would have shown zero XP and zero badges forever. It's now wired into the report generator, firing right after a report's scores are known, wrapped in its own try/catch so a gamification failure can never take down report generation.
- The same function also filtered on `round_type`, a column that never existed on `ia_interviews` (only `type`, a free-text label, did) — every query referencing it was silently failing. Added the real column, an explicit `round_type` selector in interview creation (client-supplied from a small closed set, not guessed from free text), and wired it through the whole stack: schema → API → frontend interview setup.
- `IA_Claude::MODEL` fix (from pass one) now has an actual admin UI field (Settings → AI Core → Claude Model ID) — the whole point of making it configurable was to let an admin fix a bad model ID without a redeploy; it needed a place to type the fix.
- `IA_Cost_Tracker::top_users()` joined a table via `{$wpdb->prefix}users`, which silently breaks on WordPress Multisite (the users table is global, not per-site-prefixed) — fixed to use WordPress's own correctly-resolved `$wpdb->users`.
- New frontend: Onboarding, Settings, Billing (with Razorpay checkout), History, Gamification/progress, and ATS resume-match screens — the full journey now has no missing pages between registration and every backend feature that already existed.
- New PHPUnit tests (`tests/test-enterprise-fixes.php`) covering: turn idempotency actually preventing duplicate rows, report-retry's 3-attempt cap, usage-minutes actually persisting after an interview ends, and webhook-delivery idempotency for payments — including a working `pre_http_request` stub so these run without hitting the real Claude API.
- The PDF report download (`includes/class-pdf-report.php` — a real, working, dependency-free PDF generator with a signed 1-hour download link) existed on the backend with no frontend hook at all. Wired a "Download PDF" button into the Report screen.

**Fourth pass — a systematic schema audit, done last:** I cross-referenced every single `$wpdb->insert()`/`update()`/`replace()` call in the codebase (grepped repo-wide) against the actual `CREATE TABLE` definitions in `class-activator.php`, one by one, rather than trusting each call site in isolation. This is the same technique that found the `ia_usage.date` and `ia_payments` missing-column bugs in pass one, and it found one more, worse than either:
- **`cron/class-report-generator.php`'s report-completion `$wpdb->update()`** (the call that marks a report `done` with its scores) was setting `best_turn_number` and `worst_turn_number` — columns that never existed on `ia_reports`. `$wpdb->update()` sends one SQL statement for the whole array; MySQL rejects the entire statement on an unknown column, so this wasn't a "two fields silently dropped" bug like the earlier ones — **it meant the update failed in full, every time, for every interview.** A report would sit at `status='pending'`/`'generating'` forever and the user would see an infinite loading spinner, with `class-api-reports.php`'s retry endpoint unable to help because the report was never actually marked `failed` either — it just silently never finished. This was the single most severe bug found in the whole audit (it broke the core "see your results" path for 100% of interviews) and is now fixed by adding both columns (`smallint unsigned DEFAULT NULL` — they store a turn number reference) to the `ia_reports` schema.
- Every other write call in the codebase (`ia_review_queue`, `ia_xp_events`, `ia_saved_answers`, `ia_refresh_tokens`, `ia_signup_attempts`, `ia_score_aggregates`, `ia_subscriptions`, `ia_otp_codes`, `ia_profiles` across all its call sites, `ia_turns`, `ia_interviews`) was individually checked column-by-column against its schema this pass and all are consistent — no further column-mismatch bugs found.

**Fifth pass — a WordPress hook-ordering audit:** having exhausted schema mismatches, I checked every `add_action`/`add_filter` call for ordering bugs (a callback registered from inside another hook's handler, for a hook that already fired earlier in the request). This found one more critical bug: `IA_PDF_Report::register()` was being invoked from inside the plugin's `rest_api_init` callback, and it called `add_action('init', ...)` to bind the raw PDF-download handler. `init` fires once, early in every request, well before `rest_api_init` ever runs — so that `add_action` call was always registering a callback for a hook that had already finished firing on that same request. WordPress does not retroactively invoke a newly-added callback for a hook that already ran, so **the PDF download endpoint would have silently returned a blank response on every single request, forever** — the "Download PDF" button wired into the frontend this session would never have actually worked. Fixed by splitting `IA_PDF_Report::register()` (still called from `rest_api_init`, only registers the REST route that issues the download token) from a new `IA_PDF_Report::bind_download_handler()` (called directly from the top level of the `plugins_loaded` callback in `interviewace.php`, before `init` fires). Checked every other `add_action('init', …)` call in the codebase for the same pattern — none of the others were affected.

**Sixth pass — every internal link checked against the actual React Router table:** the SPA is mounted with `basename="/app"` (`frontend/src/App.tsx`), which means any link that doesn't start with `/app` matches none of its routes and the page loads blank (there is a catch-all `*` route, but only for unmatched paths that *are* under `/app` — a path outside the basename entirely doesn't reach the router at all). Grepped every `home_url(...)` call across the backend and every public-facing template for internal app links and checked each one against `App.tsx`'s actual route table. Found the same class of bug in six places, all now fixed:
- `IA_Plan_Enforcer::can_create()`'s weekly-limit `upgrade_url` → was `/billing`, now `/app/billing` (a sibling error a few lines away in `turn()` already had this right, which is how the mismatch surfaced).
- The failed-payment email in `class-api-billing.php` → was `/billing`, now `/app/billing`.
- The "your report is ready" email in `cron/class-report-generator.php` → this one had *two* bugs stacked: missing `/app`, **and** it linked `/report/{interview_id}` when `/report/:id` (App.tsx) actually expects a *report* id, not an interview id — that route would have 404'd on the correct data type even with the prefix fixed. Changed to `/app/history/{interview_id}`, which the SPA's `ReportByInterview.tsx` correctly resolves via `GET /reports/by-interview/{interviewId}`.
- Every "Start free" / "Start practising free" / "Get started" call-to-action across the public marketing site (`templates/public/header.php`, `home.php`, `pricing.php`, `about.php`) → these linked to `/login` or `/signup`, neither of which is a real route (the SPA only knows `/app/login` and `/app/register`). This meant **the primary conversion path on every public marketing page was broken** — every visitor clicking "Start free" from the homepage, pricing page, or about page would land on a blank screen. All now point to `/app/login` / `/app/register` correctly.

**Seventh pass — a payment-integrity check on the billing flow:** `IA_API_Billing::subscribe()` was returning a hardcoded checkout amount (29900 / 49900 paise) that had no connection to either the admin-configurable `price_display` shown on the pricing page or to what Razorpay actually charges (determined solely by the plan's own configuration on Razorpay's dashboard). If an admin ever updated pricing in one place without also updating this PHP constant, customers would see a checkout confirmation that doesn't match their real bill — a trust/compliance problem, not just a cosmetic one. Fixed by fetching the plan's real amount directly from Razorpay (`GET /plans/{id}`) at subscribe time, so the confirmation always matches the actual charge with no second source of truth to drift out of sync. Also cleaned up a harmless `$uid=$uid=...` double-assignment typo in the same method while in there.

**Eighth pass — a complete route/contract audit, frontend against backend:** cross-checked every `apiFetch()` call in the frontend against the actual `register_rest_route()` calls in the backend, endpoint by endpoint. All matched — no orphaned or mismatched routes. This surfaced something different: the backend's entire answer-library and SM-2 spaced-repetition review-queue system (`get_lib`/`save_answer`/`del_answer`/`get_queue`/`submit_review`/`enqueue_answer` in `class-api-gamification.php`) was fully implemented and working, but had **zero frontend consumer** — not one API call anywhere in the React app touched it. Since the user's mandate was "nothing remains incomplete, not even overlooked gaps," this pass built it out rather than leaving it as dead backend code: `frontend/src/api/library.ts` (the client for all six endpoints), `frontend/src/pages/Library.tsx` (a searchable answer library with save/delete and "add to review queue"), and `frontend/src/pages/Review.tsx` (the actual spaced-repetition flashcard flow — reveal-then-rate against the 0/2/3/4/5 SM-2 quality scale, one card at a time, next-due handled entirely server-side). Wired into routing (`/library`, `/library/review`) and linked from the dashboard nav so it's actually discoverable, not just reachable by typing a URL.

**Ninth pass — the turn-submission idempotency path, traced end to end for a gap the earlier fix didn't fully close:** `IA_API_Interviews::turn()`'s replay branch (the one that makes retrying a duplicate turn submission safe — see the idempotency fix documented above) returned `is_complete: true` without a `report_id` when the *completing* turn was the one being replayed. The frontend (`LiveInterview.tsx`) only navigates to the report when both `is_complete` and `report_id` are present — so the one scenario this replay path exists to handle safely (a network failure on the turn that finishes the interview, then a retry) would leave the user stranded on the interview screen with no way to reach a report that had, in fact, already been generated. Fixed by looking up the existing report id in the replay branch whenever the replayed turn was the completing one — `do_end()` always creates the `ia_reports` row before the original request can return, so this lookup is always safe.

Also fixed the same broken-link pattern as the sixth pass in one more place found this round: `InterviewSetup.tsx`'s "Upgrade plan" link (shown when the weekly free-plan limit is hit) was a raw `<a href="/billing">` — outside the SPA's `/app` basename, and a hard page reload besides. Changed to a router `<Link to="/billing">`.

**Tenth pass — a genuine onboarding lockout trap, found by reading the onboarding flow end to end against `ProtectedRoute.tsx`:** `onboarding_complete` could previously only become `true` as a side effect of submitting a non-empty `target_role` (`IA_API_Profile::update()`). But `Onboarding.tsx`'s own header comment says the flow is "deliberately skippable at every step" — including the role step itself, via its own `if (!targetRole.trim()) { goNext(); return; }`. **A user who skipped every step (the flow explicitly allows this) would reach `/dashboard` with `onboarding_complete` still `false` — and `ProtectedRoute.tsx` redirects any authenticated user in that state straight back to `/onboarding`, on every single protected route.** That user would be bounced right back to the onboarding screen the instant they tried to leave it, permanently, with no error message and no way out — a full account lockout for anyone using the "skip everything" path the UI itself offers. Fixed on both sides: the backend now accepts an explicit `onboarding_complete` field on `PUT /profile` (in addition to the existing target_role side effect, kept for compatibility), and `Onboarding.tsx`'s `finish()` now sends it unconditionally regardless of which steps were actually filled in, so completing the flow — by any path, skips included — always actually completes it.

**Explicitly NOT built yet (still honest about this — not claiming these are done):**
- Admin cost-dashboard UI is WP-admin-side PHP (`admin/class-cost-dashboard.php`) and already exists/works independent of the React app — not touched, not a gap in the user-facing product.
- True SSE streaming for live-interview turns (A1's full fix) — the backend retry/idempotency half is done, but turns are still request/response, not streamed token-by-token. This is a larger architectural change (REST contract + client consumption) that needs its own dedicated pass.
- A real, mechanically-run test and build pass — see the verification-status note above; the new PHPUnit tests are written and lint-clean but not executed (no WP test environment in this sandbox), and `npm run build` still hasn't been run for the same registry-access reason as before. Both need to be run for real before production use.

**Eleventh pass — a dev-environment-only bug, found doing a manual TypeScript-style review since this sandbox cannot run `tsc`/`vite build` (see the note at the top):** `frontend/index.html` had a plain (non-module) inline `<script>` block that referenced `import.meta.env` — `import.meta` is only valid syntax inside an ES module, so a classic script containing it throws a SyntaxError the instant the browser parses it and the whole block never runs. This only affected `npm run dev` (local development against a live WP install) — the real production build is unaffected, since WordPress supplies `window.IA_CONFIG` itself via `wp_localize_script` before the app ever loads. Fixed by moving that logic into `main.tsx`, a real module, where `import.meta.env` works correctly.

**Twelfth pass — reported by the user after a real install ("home page has black screen"), root cause found in `interviewace.php` + `includes/class-activator.php`:** on activation, the plugin set the WordPress *front page* (`/`) to be the `interviewace-root` page, which is served by `templates/app-page.php` — the React app shell, whose default background is a near-black `#0F0F1A` (`react-app/dist/app.css`). This meant every fresh install's homepage showed the dark app shell instead of the actual marketing homepage (`templates/public/home.php`, at the `ia-home` slug) — and if `app.js` hadn't finished mounting yet, the visitor saw nothing but a plain black rectangle. Two compounding bugs, both fixed:
  1. `class-activator.php::create_root_page()` was setting `show_on_front`/`page_on_front` to the app-shell page. Removed — that page is only meant to be the target of the `/app/*` rewrite, not the site's homepage.
  2. `interviewace.php`'s catch-all rewrite rule (`^(?!wp-admin|wp-json|...)(.*)$`) used `.*`, which also matches the *empty* path — i.e. the bare domain `/` itself — forcibly routing the homepage request to the app shell regardless of the front-page setting. Changed to `.+` (one-or-more) so `/` now falls through to WordPress's normal front-page resolution. `/app/*` and every other non-empty path are unaffected.
  3. `class-activator.php::create_public_pages()` now explicitly sets the `ia-home` page as the WordPress front page (`show_on_front=page`, `page_on_front=<ia-home id>`), so new installs get the marketing homepage at `/` correctly from the first activation.

  **If you already installed the previous package and saw the black homepage:** you do NOT need to reinstall from scratch. Just deactivate the plugin in WP Admin → Plugins, then activate it again — `activate()` re-runs in full on every activation (not just first install), so it will correct the front-page setting on your existing site automatically. If the homepage still doesn't update after that, go to Settings → Permalinks and click "Save Changes" once (with no other changes) — this forces WordPress to rebuild its rewrite-rule cache, which is the other place the old, buggy rule could still be cached.

## Regression checklist for whoever builds and deploys this

Run through this in order after `npm run build` succeeds:

1. Fresh install: activate the plugin on a clean WP site, confirm `ia_db_version` gets set and all tables create without error.
2. Upgrade path: on a site with the *original* v2.6.8 schema and existing `ia_turns` rows (including some deliberately duplicated `(interview_id, turn_number, role)` rows), confirm activation dedupes them and the unique key applies without a dbDelta error.
3. Register → verify OTP → confirm login works, confirm 6 wrong OTP attempts locks out for 15 minutes.
4. Start an interview, submit a turn, then simulate a network failure right after (e.g. kill the connection before the response returns) — confirm retrying with the same turn number does NOT duplicate the turn or double-call Claude (check `ia_turns` row count and `ia_api_costs` for that interview).
5. Force a report generation failure (e.g. temporarily break `IA_CLAUDE_KEY`), confirm status shows `failed`, then fix the key and confirm "Regenerate report" recovers it.
6. Confirm `/wp-json/ia/v1/health` returns no `keys` field when called logged-out, and does when called as an admin.
7. Confirm the browser's Network tab shows no Deepgram/ElevenLabs key anywhere in `window.IA_CONFIG` or any response body.
8. Confirm Google OAuth login lands on `/app/auth/callback?code=...` (never `?token=...`) and completes successfully.
9. Cross-browser/device: run through auth → setup → interview → report on desktop Chrome, mobile Safari, and one Android browser at minimum.
